# Deployment, activation and recovery

## Immutable image

Publish source with a normal push to staging. Wait for CI and immutable image
release. Download image.tar.gz + SHA256SUMS from the same build-<SHA> release,
verify checksum before docker load, and verify OCI revision after loading.
Never edit runtime backend sources on the server. No floating image deployment.

Generic Compose is docker-compose.yml. Copy .env.example to a private .env (0600),
set BRIDGE_IMAGE=max-chatwoot-bridge:<full SHA>, and absolute BRIDGE_DATA_ROOT.
Compose publishes only loopback port9091. Redis has no host port and resides on
an isolated internal queue network; access is granted only to this bridge.
Credentials can be supplied as KEY_FILE instead of KEY; never commit them.
Docker runs non-root/read-only with memory limits. Prepared mode needs only Redis.
A deployment-specific overlay connects bridge to the existing Chatwoot/HTTPS networks.

Start: docker compose --env-file .env up -d --wait. Health reports prepared until
activated. /ready returns503; no webhook is processed and no external message sent.

## Activate after MAX bot moderation

1. Create the official bot in MAX business/partner platform and obtain its ID/token.
2. Create one API inbox in Chatwoot, add the staff administrator and a dedicated
   service agent. Use the agent API access token, not an operator/admin token.
3. Store MAX_BOT_ID, MAX_BOT_TOKEN, CHATWOOT_ACCOUNT_ID/INBOX_ID/API_TOKEN privately.
   Generate a random MAX_WEBHOOK_SECRET (at least32 chars). CHATWOOT_WEBHOOK_SECRET
   is the API channel signing secret generated by Chatwoot (not its client HMAC
   identifier secret). On Chatwoot4.19 this is Channel::Api#secret.
4. Publish only two HTTPS POST routes through the existing reverse proxy:
   /integrations/max/incoming → bridge:3000/max-webhook and
   /integrations/max/chatwoot → bridge:3000/chatwoot-webhook.
   Keep staff UI/API Basic Auth. Set body limit64k, access/error payload logging
   off, short connect/read timeouts. The callbacks are authenticated in the app.
5. Set the API inbox callback URL to the second route. Chatwoot must send its
   native timestamp/HMAC headers. Do not substitute an account-wide unsigned hook.
   Chatwoot SafeFetch requires a reachable public HTTPS callback, not private IPs.
6. Set BRIDGE_ENABLED=true and MAX_PUBLIC_WEBHOOK_URL to the first route, deploy
   the same immutable image. Startup verifies bot identity and API inbox access.
7. Run `docker compose exec bridge node dist/manage.js subscribe`. It checks the
   existing bot subscriptions and refuses to take over another application's URL.
   It subscribes only to message_created, supplying the MAX secret header.
8. Send a real user message, verify distinct users stay distinct, reply from
   Chatwoot, verify text/file delivery and that private notes do not leave it.
   Then restart bridge and confirm no duplicate. Test actual webhook availability.

No bot token available means prepared mode only; do not use fake credentials or
claim a completed roundtrip. No automatic greetings/FAQ/menus are introduced.

## Operations

`docker compose exec bridge node dist/manage.js status` prints queue counts only.
Health checks Redis; failed queue count needs operational monitoring. Worker errors
are controlled event names. An uncertain outgoing receipt requires checking MAX
message history before deciding whether to send a new operator reply. No automatic
command clears uncertain receipts. After repairing a transient incoming failure,
`node dist/manage.js retry-in <in-job-id>` retries the retained job; do not edit
queue keys/offsets or start a second worker replica. Manual remediation after
retention expiry may require recovering a database backup.

## Backup / restore

All queue jobs, mapping and receipts live in Redis. Use AOF always/noeviction;
keep the entire data directory, not a single AOF fragment. For a consistent backup,
stop bridge (drain workers), run redis-cli SAVE, copy dump.rdb plus private .env
and deployed SHA/Compose to a root-only archive. Retention follows infrastructure
backup policy; copies contain personal data/tokens. Verify copies before upgrade.
For restore stop both services, restore dump.rdb into an empty Redis data directory
with correct ownership, restore private config and exact image SHA, start Redis
without stale AOF files (allow fresh AOF generation), then start bridge and inspect
queue/receipts. Never flush a live queue or reuse an empty database as rollback.

## Rollback

Switch only BRIDGE_IMAGE to the previous CI SHA and retain the same Redis data and
private settings. No schema migration in this release. Keep only one running bridge.
Stopping an active bridge requires alerting the support team because MAX retains
undelivered webhook events for a limited time. Do not delete bot subscriptions with
pending events during ordinary upgrade or rollback. Restore prepared mode only
when intentionally pausing activation; it returns503 rather than acknowledging loss.
